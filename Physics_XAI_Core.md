# Physics XAI Core Pipeline

## Purpose

This document defines the production direction for the Physics part of the XAI
challenge.

The goal is not to memorize the local dataset. The goal is to solve new
questions from the same Physics scope by reasoning over code-owned formulas,
geometry templates, units, and logical rules.

Core rule:

```text
Qwen plans. Deterministic engines solve. Verifier decides confidence.
```

Qwen2.5-7B-Instruct from `models/` is allowed only as a structured planner,
classifier, extractor, or one-shot repair assistant. It must never be the
source of final numerical truth.

## Supported Scope

Only these Physics areas are in scope:

- Electric circuits.
- Resistance, voltage, current, and power.
- Capacitance and capacitor energy.
- Electric fields and electric potential.
- Coulomb force and electrostatic energy.
- Vector electrostatics with recoverable geometry.
- LC and RLC circuits.
- Inductance and inductor energy.
- Magnetic fields, solenoids, magnetic flux, and induction.

Out of scope unless explicitly added to registries:

- Mechanics unrelated to electric or magnetic fields.
- Thermodynamics.
- Optics.
- Quantum physics.
- Arbitrary free-form diagrams.
- Arbitrary symbolic equations generated by an LLM.

## API Contract

Input:

```json
{"question": "Physics question text only"}
```

Required output:

```json
{
  "answer": "...",
  "explanation": "...",
  "confidence": 0.0
}
```

Recommended output:

```json
{
  "answer": "...",
  "explanation": "...",
  "confidence": 0.95,
  "cot": ["public concise reasoning step"],
  "premises": ["formula, rule, or physical principle used"],
  "metadata": {}
}
```

`cot` is public reasoning only. It must be short, trace-derived, and free of
hidden chain-of-thought.

Controlled fallback:

```json
{
  "answer": "Uncertain",
  "explanation": "The problem could not be solved with verified Physics rules under the current time budget.",
  "confidence": 0.0,
  "metadata": {
    "status": "unsupported_or_unverified"
  }
}
```

The implementation may expose `answer: null` internally, but the public API
should use one consistent fallback. Current project tests use `"Uncertain"`.

## Data Reality

Current local file:

```text
Physics_Problems_Text_Only.csv
rows: 1,350
columns: id, question, cot, answer, unit
```

The dataset is useful for:

- Coverage measurement.
- Regression tests.
- Formula and concept discovery.
- Retrieval metadata when stripped of answers.
- Telemetry-driven improvement.

The dataset must not be used as:

- A lookup table for final answers.
- A source of answer leakage into Qwen prompts.
- A reason to hard-code problem IDs.
- A reason to write solver branches that only match one known question.

Current common answer units include:

```text
N, V/m, N/C, V, J, Ohm, A, W, F, uF, nC, pF, C, %, Hz, H, mH, cm, -
```

## Main Design Shift

The current baseline can solve many dataset rows, but its router and solver are
partly dataset-shaped:

- `router.py` contains many phrase-driven `if/elif` routes.
- `solver.py` contains many formula-specific and conceptual special cases.
- Conceptual answers often depend on exact wording.
- Some geometry cases are handled by narrow pattern branches.

The upgraded pipeline changes the center of gravity:

```text
Old:
  wording -> hard-coded route -> hard-coded solver branch

New:
  entities + targets -> formula/principle candidates -> structured plan
  -> generic equation, geometry, or logic engine -> verifier
```

The router becomes a light domain gate. The solver becomes a set of generic
engines over code-owned registries.

## High-Level Pipeline

```text
1. Receive API request.
2. Start global 55s deadline.
3. Canonicalize raw question.
4. Check verified-response cache.
5. Normalize text, symbols, quantities, units, entities, targets, and conditions.
6. Apply deterministic implicit KB rules.
7. Run light domain router.
8. Try existing high-precision deterministic fast path.
9. If verified, build trace explanation, answer-check, cache, and return.
10. If unsolved or low confidence, run Formula/Principle RAG over safe registry cards.
11. Call Qwen planner once with normalized payload and retrieved registry metadata.
12. Enforce structured JSON schema.
13. Validate plan against allowlists, units, dimensions, bindings, and trigger evidence.
14. Dispatch to deterministic engine:
    - Equation Graph Engine.
    - Spatial Vector Engine.
    - Logic/SMT Engine.
    - Multi-output Orchestrator.
15. If engine fails with a repairable strict error, call Qwen once for repair.
16. Validate repaired plan.
17. Re-run deterministic engine once.
18. Verify values, dimensions, roots, geometry, logic entailment, and target units.
19. Build deterministic explanation from execution trace.
20. Optionally run guarded Qwen explanation polish only if budget and time permit.
21. Verify polish preserves the answer exactly or equivalently.
22. Run answer checker.
23. Cache only verified and answer-checked responses.
24. Return API response.
```

This is one production pipeline. The fast path stays useful, but it is no
longer the only route to correctness.

## LLM Budget

Default maximum:

```text
2 Qwen calls per request
```

Allowed patterns:

```text
0 calls:
  cache or deterministic fast path solves and verifies

1 call:
  structured base plan

2 calls:
  base plan + one strict repair
  base plan + guarded polish
  implicit classifier + base plan
```

Optional 3-call mode is allowed only when explicitly enabled:

```text
base plan + one strict repair + guarded polish
```

If 3-call mode is used:

- The third call must be polish only.
- At least 8 seconds must remain.
- The final answer must already be verified.
- Polish cannot change numbers, units, assumptions, formulas, or target order.

Recommended default for competition safety:

```text
max_qwen_calls = 2
guarded_polish_enabled = false unless telemetry shows enough time
```

## Light Domain Router

The router should not decide a narrow formula from wording. It should classify
only the broad solving mode and domain.

Domain route values:

```text
dc_circuit
capacitor
electrostatics_scalar
electrostatics_vector
lc_rlc
magnetic_induction
conceptual_logic
multi_output
unknown
```

Answer type values:

```text
numeric
symbolic
conceptual
yes_no
multi_output
```

Router responsibilities:

- Detect obviously out-of-scope questions.
- Detect whether the question is numeric, symbolic, conceptual, yes/no, or multi-output.
- Detect whether geometry is likely needed.
- Detect whether logic/rule reasoning is likely needed.
- Preserve uncertainty instead of forcing a narrow route.

Router must not:

- Use problem IDs.
- Depend on dataset row order.
- Use answer labels from the training file.
- Pick final formulas by exact phrase when a generic planner/registry can decide.
- Return high confidence for a route that requires hidden assumptions.

The existing phrase router can remain as a fast path, but only for high
precision cases and only when its result is verified by the deterministic tail.

## Front Payload

The normalizer should produce a structured front payload that is rich enough for
generic engines.

Shape:

```json
{
  "raw_question": "...",
  "canonical_question": "...",
  "quantities": [
    {
      "id": "q0",
      "symbol": "C",
      "name": "capacitance",
      "value": 100,
      "unit": "uF",
      "si_value": 0.0001,
      "si_unit": "F",
      "dimension": "capacitance",
      "raw_text": "100 uF"
    }
  ],
  "targets": [
    {
      "id": "t0",
      "symbol": "W",
      "name": "stored energy",
      "dimension": "energy",
      "requested_unit": "J"
    }
  ],
  "conditions": [
    "ideal_capacitor",
    "voltage_known"
  ],
  "relations": [],
  "spatial_facts": [],
  "logical_assertions": [],
  "implicit_facts": [],
  "answer_type_hint": "numeric",
  "domain_hint": "capacitor"
}
```

The normalizer should extract:

- Quantities and units.
- Physical symbols.
- Target phrases.
- Target dimensions.
- Conditions such as `series`, `parallel`, `ideal`, `resonance`, `isolated`, `connected_to_battery`.
- Geometry facts such as points, distances, charges at points, midpoint, perpendicular bisector, triangle, square, rectangle.
- Logic facts such as `resonance`, `same_voltage_parallel`, `charge_conserved`, `energy_conserved`.

If extraction is uncertain, leave the field empty or low-confidence. Do not
invent missing information.

## Formula and Principle Cards

Formula RAG retrieves cards, not answers.

Each formula card is code-owned and auditable.

Formula card schema:

```json
{
  "formula_id": "capacitor_energy_voltage",
  "principle_id": "capacitor_core",
  "equation": "W = 0.5*C*U**2",
  "variables": {
    "W": {"dimension": "energy", "domain": "nonnegative", "default_unit": "J"},
    "C": {"dimension": "capacitance", "domain": "positive", "default_unit": "F"},
    "U": {"dimension": "voltage", "domain": "real", "default_unit": "V"}
  },
  "target_dimensions": ["energy"],
  "required_conditions": ["capacitor"],
  "forbidden_conditions": [],
  "description": "Energy stored in a capacitor when capacitance and voltage are known.",
  "safe_prompt_text": "For a capacitor with known capacitance and voltage, W = 1/2 C U^2."
}
```

Principle card schema:

```json
{
  "principle_id": "dc_circuit_core",
  "domain": "dc_circuit",
  "equation_ids": ["ohm_law", "power_ui", "power_i2r", "power_u2r"],
  "rules": ["series_current_same", "parallel_voltage_same"],
  "description": "Ohm law, electric power, and simple series/parallel DC relations."
}
```

Rules:

- Every formula ID in prompts must exist in code.
- Every equation must be parseable by a safe expression parser.
- Every variable must declare dimension and physical domain.
- Equations are registry data, not LLM output.
- Qwen can select formula IDs but cannot define equations.
- Retrieval examples must not include ground-truth answers or dataset CoT.

## Core Formula Families

The registry should be compact but expressive. It should model principle
families, not individual dataset rows.

### DC Circuit Core

Variables:

```text
U: voltage
I: current
R: resistance
P: power
W: energy
t: time
```

Equations:

```text
U = I*R
P = U*I
P = I**2*R
P = U**2/R
W = P*t
```

Network relations:

```text
R_series = sum(R_i)
1/R_parallel = sum(1/R_i)
series_current_same
parallel_voltage_same
kcl_node_sum
kvl_loop_sum
```

Supported tasks:

- Find voltage, current, resistance, power, or energy.
- Simple series and parallel resistance.
- Simple KCL/KVL cases when topology is recoverable.
- Internal resistance when source model is explicit.

### Capacitor Core

Variables:

```text
C: capacitance
Q: charge
U: voltage
W: energy
epsilon: permittivity
epsilon_r: dielectric constant
A: plate area
d: plate separation
```

Equations:

```text
Q = C*U
W = 0.5*C*U**2
W = Q**2/(2*C)
W = 0.5*Q*U
C = epsilon*A/d
epsilon = epsilon_r*epsilon0
```

Network relations:

```text
C_parallel = sum(C_i)
1/C_series = sum(1/C_i)
series_charge_same
parallel_voltage_same
isolated_capacitor -> Q constant
connected_to_battery -> U constant
```

Supported tasks:

- Charge, voltage, capacitance, energy.
- Parallel-plate capacitance.
- Dielectric scaling.
- Series and parallel capacitor networks when topology is recoverable.
- Charge sharing when conservation facts are explicit.

### Electrostatics Scalar Core

Variables:

```text
q, q1, q2: charge
r: distance
F: force magnitude
E: electric field magnitude
V: electric potential
W: electrostatic energy/work
k: Coulomb constant
```

Equations:

```text
F = k*abs(q1*q2)/r**2
E = k*q/r**2
V = k*q/r
W = k*q1*q2/r
F = q*E
E_uniform = U/d
```

Notes:

- Scalar magnitude formulas must still preserve sign when the target asks for
  polarity, potential, or charge sign.
- `abs()` is allowed only for magnitude targets.
- Signed quantities must use signed domains.

### Electrostatics Vector Core

Vector formulas:

```text
r_vec = point_target - point_source
r = norm(r_vec)
E_vec = k*q*r_vec/r**3
F_vec_on_target = q_target*E_vec
F_vec_pair = k*q_source*q_target*r_vec/r**3
```

Supported geometry templates:

```text
two_points_collinear
point_on_line_segment
point_on_midpoint
point_on_perpendicular_bisector
external_point_on_line
equilateral_triangle_vertex
right_isosceles_triangle_vertex
triangle_from_three_sides
triangle_from_two_sides_included_angle
square_center
square_vertex
rectangle_center
rectangle_vertex
regular_polygon_center
```

Rules:

- Qwen must not invent coordinates.
- Qwen selects a template and binds named points, distances, and charges.
- The spatial engine constructs coordinates deterministically.
- If no template fits, return `geometry_ambiguous`.
- If direction is requested, return magnitude and direction.
- If only magnitude is requested, verify components internally.

### LC and RLC Core

Variables:

```text
L: inductance
C: capacitance
R: resistance
f: frequency
omega: angular frequency
T: period
XL: inductive reactance
XC: capacitive reactance
Z: impedance
I: current
U: voltage
P: active power
cos_phi: power factor
```

Equations:

```text
omega = 2*pi*f
XL = omega*L
XC = 1/(omega*C)
Z = sqrt(R**2 + (XL - XC)**2)
I = U/Z
cos_phi = R/Z
P = U*I*cos_phi
omega0 = 1/sqrt(L*C)
f0 = 1/(2*pi*sqrt(L*C))
T = 2*pi*sqrt(L*C)
```

Logic rules:

```text
series_rlc and resonance -> XL = XC
XL = XC -> Z = R
XL = XC -> cos_phi = 1
XL > XC -> circuit_is_inductive
XL < XC -> circuit_is_capacitive
```

Supported tasks:

- Reactance, impedance, resonance frequency, period.
- Current, voltage, power factor.
- Conceptual resonance questions.
- Frequency scaling when the relevant relation is recoverable.

### Inductance and Magnetic Core

Variables:

```text
L: inductance
I: current
W: magnetic energy
B: magnetic field
N: turns
n: turn density
l: solenoid length
A: area
Phi: magnetic flux
theta: angle
emf: induced electromotive force
mu0: magnetic constant
mu_r: relative permeability
```

Equations:

```text
W = 0.5*L*I**2
B = mu0*n*I
n = N/l
Phi = B*A*cos(theta)
emf = N*abs(DeltaPhi)/Deltat
emf_self = L*abs(DeltaI)/Deltat
L_solenoid = mu0*mu_r*N**2*A/l
```

Optional vector formulas:

```text
F = abs(q)*v*B*sin(theta)
F = B*I*l*sin(theta)
```

Supported tasks:

- Inductor energy.
- Solenoid magnetic field.
- Magnetic flux.
- Faraday induction.
- Self-induction.
- Simple magnetic force when angle and direction are explicit.

## Formula RAG

Retrieval is used to choose candidate registry cards. It is not used to answer
the task.

Index sources:

- Formula cards.
- Principle cards.
- Geometry template cards.
- Logic rule cards.
- Curated pattern labels with no answers.

Do not index:

- Dataset final `answer`.
- Dataset `cot`.
- Final numeric values.
- Problem-specific solution traces.

Retrieval query:

```text
canonical question
+ extracted targets
+ dimensions
+ conditions
+ domain hint
+ spatial/logical facts
```

Retrieval output:

```json
[
  {
    "score": 0.91,
    "card_type": "formula",
    "formula_id": "capacitor_energy_voltage",
    "principle_id": "capacitor_core",
    "target_dimensions": ["energy"],
    "required_conditions": ["capacitor"],
    "safe_prompt_text": "For a capacitor with known capacitance and voltage, W = 1/2 C U^2."
  }
]
```

Rules:

- Retrieve top 5-12 cards depending on domain.
- Include disagreement metadata when candidates conflict.
- Prefer cards whose variables connect known dimensions to requested targets.
- Do not let retrieval alone set confidence above verifier confidence.

## Qwen Planner Contract

Qwen can:

- Select `domain_route`.
- Select `task_mode`.
- Select whitelisted `formula_ids`.
- Select whitelisted `principle_ids`.
- Select whitelisted `geometry_template_id`.
- Select whitelisted `logic_rule_ids`.
- Bind extracted quantities to formula variables.
- Bind targets to formula variables.
- Propose solve strategy.
- Produce short public decision notes.

Qwen cannot:

- Compute final numeric answers.
- Add new formulas.
- Add new constants.
- Add new units.
- Add new quantities not present in the question or implicit KB.
- Invent diagrams or coordinates.
- Generate Python code.
- Override executor, verifier, or answer checker.
- Use hidden/free-form chain-of-thought.

Planner output schema:

```json
{
  "status": "ok",
  "domain_route": "capacitor",
  "task_mode": "equation",
  "answer_type": "numeric",
  "targets": [
    {
      "target_id": "t0",
      "symbol": "W",
      "dimension": "energy",
      "requested_unit": "J"
    }
  ],
  "formula_ids": ["capacitor_energy_voltage"],
  "principle_ids": ["capacitor_core"],
  "geometry_template_id": null,
  "logic_rule_ids": [],
  "variable_bindings": {
    "C": "q0",
    "U": "q1",
    "W": "t0"
  },
  "spatial_bindings": {},
  "logical_assertions": [],
  "implicit_rule_ids": [],
  "solve_strategy": "direct",
  "decision_notes": [
    "The target is capacitor stored energy.",
    "Capacitance and voltage are given."
  ],
  "confidence": 0.82
}
```

Allowed `task_mode` values:

```text
equation
geometry
logic
multi_output
unsupported
```

Allowed `solve_strategy` values:

```text
direct
graph
sequential
simultaneous
spatial_vector
logic_entailment
```

Planner confidence is advisory only. It cannot raise final confidence above
the verifier confidence.

## Plan Validator

Validator rejects:

- Invalid JSON.
- Unknown status.
- Unknown domain route.
- Unknown task mode.
- Unknown answer type.
- Empty targets.
- Unknown formula, principle, geometry, logic, or implicit IDs.
- Formula IDs not present in retrieved/allowed registry cards.
- Variable bindings that reference missing quantity or target IDs.
- Variable binding dimension mismatch.
- Missing required variables for selected formulas.
- Target dimensions incompatible with selected formulas.
- Conditions required by formula cards but absent from question/implicit facts.
- Forbidden conditions present.
- Geometry template missing required point, distance, charge, or target facts.
- Logic rules missing required facts.
- Numeric answer supplied by Qwen.
- Natural-language notes that contradict structured fields.
- Implicit constants without trigger evidence.
- Retrieved example answers or dataset CoT in plan fields.

Validator lowers confidence when:

- JSON repair was needed.
- Formula RAG was needed.
- Qwen repair was used.
- Geometry assumptions were required.
- Logic entailment is weak but not contradictory.
- Multiple candidate formulas remain plausible.

Unknown IDs are hard failures. A known ID can still be rejected when its
variables, units, preconditions, or target compatibility do not match.

## Equation Graph Engine

The equation engine is the main replacement for hard-coded solver branches.

Inputs:

```text
front payload
validated formula/principle IDs
variable bindings
targets
```

Process:

```text
1. Load equation cards from registry.
2. Convert all bound givens to SI.
3. Build a bipartite graph:
   variable nodes <-> equation nodes.
4. Mark known variables from givens and implicit facts.
5. Mark requested target variables.
6. Select minimal connected equation subset from knowns to targets.
7. Reject if graph is disconnected.
8. Reject if degrees of freedom are insufficient.
9. Prefer direct algebra when one equation has one unknown.
10. Use SymPy for small systems.
11. Use bounded numerical fallback only for whitelisted families.
12. Filter roots by physical domain.
13. Substitute result back into equations and verify residuals.
14. Convert SI result to target unit.
15. Return trace.
```

Graph selection rules:

- Prefer equations that reduce unknown count toward targets.
- Avoid unrelated equations from the same principle family.
- Do not send an entire principle family to SymPy.
- If target 1 is a needed intermediate for target 2, sequential solving is allowed.
- If two targets are coupled in the same minimal subset, use simultaneous solving.
- If multiple valid paths exist, solve each or choose the smallest verified path.
- If paths disagree, return `overdetermined_conflict`.

Root filtering:

- `positive`: mass, resistance, capacitance, inductance, distance magnitude,
  frequency magnitude, period duration, energy magnitude, area.
- `nonnegative`: elapsed time, power magnitude, field magnitude, force magnitude.
- `real`: signed charge, current, voltage, potential, displacement, vector components.
- Do not drop negative values unless the variable domain forbids them.
- If multiple physically valid roots remain, return `ambiguous_solution`.

Numerical fallback:

- Allowed only for whitelisted families.
- Requires explicit bounds.
- Requires dimensional validation first.
- Requires substitution residual check.
- Caps confidence.

## Spatial Vector Engine

Use this for electrostatic vector questions.

Inputs:

```text
geometry_template_id
point bindings
distance/angle bindings
charge bindings
target point or target charge
requested output: magnitude, direction, components, or force/field
```

Process:

```text
1. Validate template and required facts.
2. Construct local coordinates deterministically.
3. Place charges and target points.
4. For each source charge, compute vector contribution.
5. Sum components.
6. Compute magnitude and direction if requested.
7. Verify symmetry cancellations when expected.
8. Return vector trace.
```

Trace should include:

- Template ID.
- Coordinate construction.
- Source contributions.
- Component sums.
- Final magnitude.
- Direction convention.
- Any assumptions.

Failure modes:

```text
geometry_template_missing
geometry_ambiguous
missing_distance
missing_charge_location
target_point_ambiguous
direction_convention_ambiguous
```

Qwen repair can change only the template ID or bindings, never raw coordinates.

## Logic and SMT Engine

Conceptual questions should be solved by rule entailment, not by exact phrase
answers.

Logic facts:

```text
domain(series_rlc)
condition(resonance)
relation(XL = XC)
property(parallel_branches_same_voltage)
state(isolated_capacitor)
state(connected_to_battery)
quantity_constant(Q)
quantity_constant(U)
```

Logic rules:

```text
series_rlc and resonance -> XL = XC
XL = XC -> Z = R
XL = XC -> power_factor = 1
XL > XC -> circuit_is_inductive
XL < XC -> circuit_is_capacitive

parallel_circuit -> branch_voltage_equal
series_circuit -> branch_current_equal

isolated_capacitor -> Q constant
connected_to_battery -> U constant
C = epsilon*A/d

ideal_lc -> total_energy_constant
ideal_lc -> electric_energy + magnetic_energy = total_energy
magnetic_energy = 0.5*L*I**2
electric_energy = 0.5*C*U**2

faraday_lenz -> induced_emf_opposes_flux_change
```

Engine options:

- A simple forward-chaining rule engine for most cases.
- A small SMT layer for yes/no equality/inequality checks.
- SymPy relations for proportionality questions.

Conceptual output must include:

- Entailed answer.
- Supporting rules.
- Trigger facts from question.
- A trace of inference steps.

Failure modes:

```text
logic_no_entailment
logic_contradiction
missing_required_fact
unsupported_conceptual_relation
```

No confident conceptual answer is allowed without a rule trace.

## Multi-Output Orchestrator

Multi-output questions must preserve target order.

Process:

```text
1. Parse ordered target list.
2. For each target, build or reuse a plan segment.
3. Detect shared intermediate variables.
4. Solve independent targets independently.
5. Solve coupled targets simultaneously.
6. Verify each segment.
7. Format output with stable separators.
```

Rules:

- A failed later target does not invalidate an earlier verified target.
- If later targets depend on a failed target, return partial result with low confidence.
- Each target gets a trace segment.
- Answer checker verifies order and units.

## Self-Correction Loop

Repair is useful, but it must be strict.

Use repair only when:

- The base plan was schema-valid or nearly schema-valid.
- The deterministic engine produced a structured, repairable error.
- Time remains.
- No previous repair has been used.

Strict error trace shape:

```json
{
  "stage": "equation_graph",
  "error_code": "graph_disconnected",
  "targets": ["W"],
  "known_variables": ["C"],
  "missing_variables": ["U"],
  "selected_formula_ids": ["capacitor_energy_voltage"],
  "candidate_formula_ids": ["capacitor_energy_charge"],
  "validator_issues": [],
  "engine_issues": ["target_not_connected_to_knowns"]
}
```

Qwen repair may change:

```text
formula_ids
principle_ids
variable_bindings
target_mapping
solve_strategy
geometry_template_id
spatial_bindings
logic_rule_ids
logical_assertions
```

Qwen repair may not:

```text
add numeric quantities
add formulas
add constants
add units
invent geometry coordinates
invent assumptions without trigger text
change the raw question
return a final answer
```

Repair confidence caps:

```text
repair used -> max 0.82
repair changed formula family -> max 0.75
repair changed geometry template -> max 0.72
repair added implicit rule with trigger evidence -> max 0.70
repair plus numerical fallback -> max 0.65
repair failed -> max 0.45
```

Repair is never repeated.

## Unit Policy

Use a project-owned unit layer.

Flow:

```text
raw value + raw unit -> normalized unit -> SI value -> solve -> target unit -> trace
```

Rules:

- Convert all numeric inputs to SI before solving.
- Pass plain numbers to SymPy.
- Keep unit and dimension metadata outside symbolic expressions.
- Convert final SI values to requested target units.
- Verify dimensions before formatting.
- Preserve every conversion in trace.
- Treat `%`, `ratio`, `times`, `Yes`, `No`, and `-` as controlled dimensionless categories.

Do not use `sympy.physics.units` in the hot path.

## Implicit Knowledge Base

Implicit constants and defaults must be deterministic and auditable.

Examples:

```json
{
  "school_coulomb_constant": {
    "adds": {"k": "9e9 N*m^2/C^2"},
    "triggers": ["in air", "in vacuum", "point charges", "Coulomb law"]
  },
  "vacuum_permittivity": {
    "adds": {"epsilon0": "8.8541878128e-12 F/m"},
    "triggers": ["air capacitor", "vacuum", "parallel plate"]
  },
  "magnetic_constant": {
    "adds": {"mu0": "4*pi*1e-7 N/A^2"},
    "triggers": ["long solenoid", "air core"]
  },
  "ideal_lc": {
    "adds": {"lossless": true},
    "triggers": ["ideal LC", "lossless LC"]
  }
}
```

Rules:

- A rule can be applied only when text triggers it or Qwen selects it with a
  trigger span that exists in the question.
- Implicit facts must appear in trace and premises.
- Qwen cannot create new implicit rules.
- Validator can reject Qwen-selected implicit rules.

## Verifier Gate

Verifier checks:

- Solver result is finite.
- Formula/principle/rule/template IDs are known.
- Unit dimensions match targets.
- Every required variable is substituted.
- Unit conversion trace exists.
- Equation residuals are within tolerance.
- Roots satisfy physical domains.
- Symbolic expressions simplify consistently.
- Vector components and magnitude/direction agree.
- Logic answers are entailed by rule trace.
- Multi-output targets each have status.
- Explanation references only trace-supported premises.
- Final answer string matches executor output after answer checker normalization.

No high-confidence result is returned unless verifier passes.

Confidence caps:

```text
verifier fails -> max 0.45
schema repair used -> max 0.82
Qwen plan used -> max 0.90
Formula RAG needed -> max 0.88
Qwen repair used -> max 0.82
geometry template assumption -> max 0.72
logic weak entailment -> max 0.75
numerical fallback -> max 0.75
partial multi-output -> max 0.70
timeout fallback -> 0.0
```

## Answer Checker

`answer_check.py` normalizes and checks final answer formatting.

Responsibilities:

- Parse numeric values and units.
- Compare equivalent units.
- Normalize percentages, ratios, and factors.
- Normalize yes/no labels.
- Normalize symbolic expressions.
- Verify multi-output separator order.
- Ensure public answer matches verified result.
- Prevent raw Qwen text from becoming an answer.
- Allow cache writes only for verified and answer-checked responses.

## Explanation Builder

Primary explanation is deterministic and trace-based.

Equation template:

```text
Use {formula_or_principle}. Convert {unit_conversions}. The equation graph selects {equations}. Substitute {values}. Therefore, {answer}.
```

Geometry template:

```text
Use electrostatic superposition. Build the {geometry_template_id} geometry, compute each vector contribution, sum components, then convert to the requested magnitude/direction: {answer}.
```

Logic template:

```text
Use {rules}. From the question, {facts}. These imply {entailed_statement}. Therefore, {answer}.
```

Explanation rules:

- Explanation must be concise.
- Explanation must mention only formulas, facts, and assumptions in trace.
- If Qwen polish changes or omits the verified answer, discard it.
- If no verified trace exists, return controlled fallback.

## Guarded Polish

Polish is optional. It should not be needed for correctness.

Use only when:

- Final answer is already verified.
- Enough time remains.
- LLM budget allows it.
- The deterministic explanation is too mechanical.

Inputs to Qwen:

- Immutable final answer.
- Immutable target units.
- Execution trace.
- Allowed formulas and rules.

Qwen may:

- Improve readability.
- Rephrase trace into teacher-like English.

Qwen may not:

- Change answer.
- Change unit.
- Add assumptions.
- Add formulas.
- Add reasoning not in trace.

After polish:

- Extract answer from polished text.
- Compare to verified answer with unit-aware equivalence.
- Accept only if equivalent.
- Otherwise discard polish.

  "explanation": "The problem exceeded the current Physics solving time budget.",
  "confidence": 0.0,

Expected timeouts must not become HTTP 500 errors.

## Cache Policy

Cache key:

```text
sha256(canonical_raw_question)
```

Canonicalization:

- Unicode normalize.
- Trim whitespace.
- Collapse repeated whitespace.
- Normalize visually equivalent micro symbols.
- Preserve mathematical meaning.

Cache value:

```json
{
  "answer": "...",
  "explanation": "...",
  "confidence": 0.95,
  "cot": [],
  "premises": [],
  "trace": {},
  "plan": {},
  "verifier": {},
  "answer_checker": {}
}
```

Cache only:

- Verified responses.
- Answer-checked responses.
- Responses with deterministic trace.

Do not cache:

- Invalid plans.
- Failed repairs.
- Low-confidence hallucination fallbacks.
- Raw Qwen outputs.
- Timeout fallbacks.

## Migration Plan

### Phase 1: Registry Upgrade

- Move formula metadata from ad hoc execution branches into formula cards.
- Add equation strings, dimensions, domains, and preconditions.
- Add principle cards for the six core families.
- Add tests that every formula card parses and declares all variables.

### Phase 2: Generic Equation Engine

- Build `equation_graph.py`.
- Implement minimal connected subset selection.
- Implement one-equation direct solve.
- Add supervised SymPy solve for small systems.
- Verify residuals and unit dimensions.
- Route unsolved fast-path cases to equation engine.

### Phase 3: Planner Integration

- Add `variable_bindings` and `task_mode` to planner schema.
- Feed Qwen only safe formula/principle cards.
- Validate Qwen output strictly.
- Keep fast path first for latency.

### Phase 4: Spatial Vector Engine

- Replace narrow Coulomb/electric-field special cases with geometry templates.
- Add deterministic coordinate builders.
- Add vector contribution traces.
- Add tests for symmetry and known geometry cases.

### Phase 5: Logic Engine

- Extract conceptual phrase answers into logic rules.
- Add forward chaining and simple entailment.
- Support yes/no and proportionality questions.
- Require rule traces for conceptual confidence.

### Phase 6: Repair Loop

- Add structured error traces.
- Add one-shot Qwen repair.
- Enforce repair allowlist.
- Add confidence caps.
- Add tests where repair fixes wrong formula binding without adding data.

### Phase 7: Anti-Overfit Evaluation

- Add paraphrase tests for solved dataset rows.
- Add synthetic out-of-dataset questions from formula cards.
- Add variable renaming tests.
- Add unit variation tests.
- Add geometry template variation tests.
- Add concept wording variation tests.

## Anti-Overfitting Rules

Never use:

- Problem IDs in router or solver.
- Dataset answer strings in inference prompts.
- Dataset CoT in inference prompts.
- Exact full-question matching.
- Branches whose only purpose is one known row.
- Hard-coded final answers for conceptual questions without rule entailment.

Prefer:

- Dimension and target matching.
- Formula graph connectivity.
- Registry preconditions.
- Unit and residual verification.
- Geometry templates.
- Logic facts and rules.
- Paraphrase tests.

Acceptable fast-path heuristics:

- High-precision phrase checks for common forms.
- Early rejection of unsupported cases.
- Latency shortcuts that still pass verifier.

Fast-path heuristics must be bypassable. If they fail or are uncertain, the
generic path should attempt to solve.

## Success Criteria

The upgrade is successful when:

- Existing dataset accuracy does not regress materially.
- More unsolved rows become solved through generic engines, not special cases.
- Paraphrase tests pass without new route branches.
- Synthetic out-of-dataset problems solve when covered by registry principles.
